Análise do Projeto de Referência: Hermes Agent Hermes Agent (Nous Research, MIT License) é um agente de IA de propósito geral, open source, escrito majoritariamente em Python 3.11+, com um componente Node.js dedicado à automação de navegador. Não foi desenhado especificamente como um robô de RPA para seguradoras — é um agente conversacional multiplataforma (&quot;o único agente com loop de aprendizado embutido&quot;, conforme o próprio README) — mas sua arquitetura de execução local, comunicação e sistema de conectores modulares é diretamente aproveitável para o objetivo do BMF IA OS. 1.1 Como o Agente Local É Estruturado e Executado O Hermes Agent roda como um processo Python de longa duração, com dois pontos de entrada principais: uma CLI interativa (hermes) e um processo de gateway (hermes gateway) que fica sempre ativo. A execução de comandos e ferramentas acontece através de múltiplos backends de terminal intercambiáveis — local (subprocess direto), Docker, SSH remoto, e sandboxes serverless (Modal, Daytona) — selecionáveis por configuração, sem alterar o código do agente. Achado relevante para o BMF IA OS: o mesmo agente pode rodar tanto direto na máquina do usuário quanto isolado em um container ou sandbox remoto, com a mesma interface de execução. Isso valida a decisão do BMF IA OS (C4-DOC-001) de manter paridade de ambiente entre local e cloud, aplicando o mesmo princípio a um novo componente: o agente instalado no computador do corretor. 1.2 Comunicação entre o Agente e a Aplicação Principal Duas camadas de comunicação coexistem no Hermes Agent, cada uma adequada a um propósito diferente: Gateway de mensageria: um processo central mantém conexões simultâneas com múltiplas plataformas (Telegram, Discord, Slack, WhatsApp, Signal, Matrix, webhook genérico), cada uma implementando uma interface comum (BasePlatformAdapter) com métodos connect(), disconnect(), send() e um handler de mensagens recebidas. ACP (Agent Client Protocol): um protocolo estruturado, baseado em sessões, usado para integração com editores/IDEs — troca mensagens tipadas (PromptResponse, eventos de progresso de ferramenta, callbacks de aprovação) em vez de texto livre. Achado relevante: o padrão ACP — sessão, eventos tipados, callback de aprovação antes de executar uma ação sensível — é estruturalmente muito próximo do que o BMF IA OS já implementa com o Escalation Handler e a Matriz de Autoridade (EA-DOC-001, Seção 7.3). Isso confirma que o desenho já existente do BMF IA OS está alinhado com o estado da arte para este tipo de sistema. 1.3 Interação com Aplicações Desktop e Sistemas Web Este é o ponto mais diretamente aplicável ao problema da Porto Seguro. O Hermes Agent usa uma técnica específica para automação web: em vez de &quot;ler a tela&quot; via captura de imagem e visão computacional (caro, lento, frágil), ele usa a árvore de acessibilidade do navegador (ariaSnapshot) como representação textual da página. Cada elemento interativo recebe uma referência curta (@e1, @e2...) que o modelo de linguagem usa para clicar, digitar ou navegar — sem nunca precisar &quot;ver&quot; a página como imagem. A automação de navegador roda sobre uma ferramenta CLI (agent-browser) que abstrai múltiplos backends por trás de uma interface comum (CloudBrowserProvider): Chromium local headless, Browserbase (nuvem), Browser Use (nuvem), e Camoufox — um Firefox especializado em evitar detecção de automação, relevante quando o sistema-alvo tenta bloquear bots. Limitação identificada, importante para o BMF IA OS: o Hermes Agent cobre bem automação web e execução de comandos/CLI, mas não inclui automação nativa de interface desktop (não há integração com Windows UI Automation, nem bibliotecas como pywinauto). Ele usa vision_tools.py apenas para analisar imagens já existentes (ex.: uma captura de tela anexada pelo usuário), não para pilotar uma aplicação desktop em tempo real. Se algum sistema usado pela BMF for um aplicativo desktop nativo (não web), essa capacidade precisa ser adicionada — não está pronta no projeto de referência. 1.4 Como o Agente Recebe Tarefas, Executa Ações e Retorna Resultados O ciclo é: a plataforma de origem (Telegram, ACP, etc.) entrega uma mensagem ao gateway → o gateway identifica a sessão e repassa ao loop do agente → o agente decide quais ferramentas invocar, consultando o Tool Registry → cada ferramenta executa e retorna um resultado estruturado → o resultado é formatado e devolvido pela mesma plataforma de origem. Chamadas sensíveis passam por um callback de aprovação (make_approval_callback, em acp_adapter/permissions.py) antes de executar. 1.5 Modularidade para Novos Conectores Este é o achado arquitetural mais valioso do repositório. O Hermes Agent usa o mesmo padrão em três camadas diferentes, todas com o mesmo princípio: interface abstrata (ou contrato de registro) + auto-descoberta, sem exigir alteração do núcleo para adicionar um novo conector. Proposta de Arquitetura — BMF Local Agent A proposta não substitui a arquitetura já construída (EA-DOC-001 a DM-DOC-002) — ela estende o Integration Hub (C4-DOC-001, Seção 3; C4-DOC-002, Seção 2) com um novo tipo de conector: em vez de um conector que faz uma chamada HTTP a uma API de terceiro, o BMF Local Agent é um conector que executa em uma máquina fora do controle direto do BMF IA OS — o computador do corretor — e se conecta de volta ao Integration Hub. Isso resolve o gargalo descrito no mandato (sistemas sem API pública, como a Porto Seguro) sem duplicar a governança já existente: toda ação continua passando pelo Tool Broker e pelo Escalation Handler antes de ser despachada, e todo resultado continua sendo auditado na mesma tabela auditoria do DM-DOC-001. 3. Estratégia de Segurança e Permissões 6.1 Princípios Conexão de saída apenas: o Local Agent inicia a conexão com o Integration Hub; nenhuma porta é aberta no computador do cliente. Isso elimina a necessidade de exceções de firewall e reduz a superfície de ataque a praticamente zero na direção de entrada. Credenciais do cliente nunca saem da máquina do cliente: a senha do corretor na Porto Seguro fica no Credential Vault local, criptografada pelo cofre nativo do sistema operacional. O BMF IA OS nunca vê essa senha em texto plano — apenas instrui &quot;use a credencial cadastrada para o conector Porto Seguro&quot;. A governança já existente não é duplicada, é reaproveitada: o Tool Broker e a Matriz de Autoridade (EA-DOC-001 §7.3) decidem se uma ação pode prosseguir antes mesmo de a tarefa ser despachada ao Local Agent — mover a execução para a borda não move a decisão de governança. Menor privilégio por conector: cada conector do Local Agent declara explicitamente quais domínios/aplicativos pode tocar (allowlist), no mesmo espírito do BASS Módulo 7 (Ferramentas) já usado pelos agentes de IA. Assinatura de código: o executável do Local Agent e cada atualização são assinados digitalmente; o agente verifica a assinatura antes de aplicar qualquer atualização, prevenindo injeção de código malicioso via update. Pareamento por token de matrícula: cada instalação do Local Agent é vinculada à conta do BMF IA OS por meio de um token de enrolamento de uso único (o mesmo padrão usado por runners de CI self-hosted) — nunca um segredo fixo embutido no instalador. 6.2 O Que Muda na Auditoria Nenhuma tabela nova é necessária. O Local Agent grava na mesma tabela auditoria do DM-DOC-001, com um agente_id apontando para um novo tipo de registro em agentes_ia (&quot;conector local&quot;, análogo a um agente Classe C, mas fisicamente remoto). O CGO IA continua sendo responsável por auditar esses registros exatamente como audita qualquer outro agente. 7. Estratégia de Atualização do Agente Mecanismo Descrição Heartbeat com versão A cada heartbeat, o Local Agent reporta sua versão instalada; o Integration Hub sinaliza se uma atualização é necessária, sem forçar a instalação imediatamente Artefato assinado Cada nova versão é publicada como um binário assinado digitalmente; o agente baixa, verifica a assinatura e só então substitui o binário anterior Troca segura (swap on restart) A atualização é aplicada como uma troca de binário no próximo reinício do processo, nunca sobrescrevendo um processo em execução — mesmo padrão do comando hermes update Rollback automático O binário da versão anterior é mantido; se a nova versão falhar em um autoteste pós-atualização (ex.: não consegue reconectar ao Integration Hub), o agente reverte automaticamente Lançamento faseado (canary) Novas versões podem ser direcionadas a um subconjunto de instalações antes do rollout completo, permitindo detectar problemas antes de afetar todos os corretores 8. Como Criar Novos Módulos/Conectores Sem Alterar a Arquitetura Principal Mesmo padrão comprovado no Hermes Agent (Seção 1.5) e já usado no Connector Registry do Integration Hub (C4-DOC-002): interface fixa + auto-descoberta. 8.1 Contrato de um Conector do Local Agent Todo conector implementa quatro métodos obrigatórios: nome() — identificador único do conector (ex.: &quot;porto_seguro&quot;) dominios_permitidos() — lista de domínios/aplicativos que este conector tem permissão de tocar (allowlist de segurança) autenticar() — recupera a credencial do Credential Vault e estabelece a sessão (browser ou desktop) executar(acao, payload) — executa a ação solicitada e retorna um resultado estruturado no mesmo formato usado pelos conectores do Integration Hub (C4-DOC-002, Seção 2) Para adicionar um novo conector (ex.: uma segunda seguradora sem API), basta criar um novo arquivo que implementa esse contrato e colocá-lo na pasta de conectores do Local Agent — o Connector Registry local o descobre automaticamente na inicialização, sem qualquer alteração no Connection Manager, no Task Receiver ou em qualquer outro componente central. O mesmo vale do lado do Integration Hub: o Task Dispatcher não precisa saber o que cada conector faz — apenas para qual instância de Local Agent (e qual conector nomeado) rotear a tarefa, exatamente como o Connector Registry central já faz hoje com CRM, seguradoras e e-signature (C4-DOC-002, Seção 2). 9. Riscos e Recomendações Complementares Risco Recomendação Termos de Uso de terceiros Antes de automatizar o portal da Porto Seguro (ou qualquer outra seguradora), submeter os Termos de Uso do portal do corretor à análise jurídica — a automação deve operar como extensão do uso legítimo já autorizado ao corretor, não como acesso não autorizado Fragilidade de UI Priorizar, sempre que existir, a API oficial sobre a automação de interface — o padrão de conector modular (Seção 8) permite trocar a implementação de um conector de &quot;automação de UI&quot; para &quot;chamada de API&quot; no futuro, sem alterar o restante da arquitetura Dependência da máquina do corretor O Local Agent deve rodar como serviço/daemon com reinício automático, e reportar seu status de saúde no heartbeat (Seção 7), para que o CTO IA detecte agentes offline Automação desktop ainda não validada O Desktop Automation Engine (Seção 5) é o único componente sem precedente comprovado no Hermes Agent — recomenda-se um piloto controlado com um único sistema desktop antes de expandir a cobertura 11.
